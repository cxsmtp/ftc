# Agent Audit Memory

Operator-provided audit context for future Codex runs on this app.

Future audits should treat the following as established unless the operator says otherwise:

- Do not report the accepted raw-secret-at-rest issue.
- LinkedIn sign-in and sign-up no longer exist (removed by operator order, 28 Oct 2026). An account created through LinkedIn before then signs in with an emailed code and is treated like any other account.
- Regular admins changing non-admin emails is acceptable.
- Privileged `verify` / `approve` behavior is by design.
- There are no password-reset links: a forgotten password is an emailed-code sign-in followed by a new password. An admin showing a participant a sign-in code at the desk (only for an approved participant who has never signed in) and an admin emailing a participant a sign-in code are by design.
- Emails and nicknames are intended to be case-insensitive everywhere.
- Unicode case-insensitive identity handling was remediated by restricting identity inputs to printable ASCII; this landed for nicknames at v7.2.9+ and for emails at v7.7.12, and is enforced on every identity write path. Do not report Unicode case-insensitivity, and do not report the ASCII restriction itself as exclusionary — it is what makes the NOCASE uniqueness indexes a complete guarantee.
- Regular admins reading the superadmin guide/help content is acceptable by design.
- The built-in superadmin password remaining anonymously rotatable after the cooldown/threshold logic is acceptable by design.
- Docker/Compose host data and upload directories are created manually with the correct ownership before deployment; do not report first-run bind-mount ownership as an issue.
- The application is deployed behind an AWS load balancer, not a host-local reverse proxy. Publishing/listening on `0.0.0.0:3000` is required and acceptable by design; do not report it as direct-backend exposure.
- Production build hosts do not contain `smoke-data-*` artifacts; do not report the theoretical Docker build-context race that could copy those local smoke-test artifacts into an image.
- The audit JSONL mirror is intentionally deferred and eventually consistent; temporary absence of freshly committed events from the Logs UI is acceptable by design.
- The absence of a participant-facing notice that enrolment sends the participant's name and email to the customer's Checkmarx One realm is acceptable by design. Do not report it, and do not propose a consent checkbox — that was rejected twice on the grounds that a tick whose only alternative is not attending is not freely given. One related fact is also accepted, by a separate decision: `competitions.cxone_disabled` has no normalisation migration. Booth Events and Programs created before v8.2.0 may still carry 0 against their kind's default of 1, which leaves Checkmarx One provisioning on, so accounts are created wherever a per-event or global Checkmarx One key is configured. Until v8.0.4 the server stored an omitted value as 0 on every create path, and until v8.2.0 the create form always sent the box, unticked unless the admin ticked it. How many such rows exist has not been measured. A blanket migration is not a safe remedy, because for those rows a 0 an admin chose cannot be told apart from one that was forced. The operator decided on 25 Nov 2026 that no action is needed, without counting the rows; do not report it. A 0 on an event created since v8.2.0 is not this gap: the create form now pre-ticks the box from the kind's default, and a later change of kind deliberately keeps the stored value, which the edit form shows and the admin can change. Erasure is the separate entry below.
- Deleting a participant removes, from the customer's Checkmarx One realm, the accounts this platform created and recorded in its `cxone_realm_accounts` ledger (since v8.12.7). There are two paths. If the participant is deleted while their own provisioning job is still running, that job withdraws the account it created in that run after a local ownership check (the operator's v8.12.6 ruling). Otherwise the deletion stamps their ledger rows in its own transaction, and a background runner deletes each account only after re-proving, against the realm's own record, that it is the one the platform made. Do not report that erasure does not propagate to the realm for those accounts. By design the platform does not delete:
  - an account it did not create — one that already existed and the participant was only matched to. That account belongs to the tenant's administrator. The ledger decides this, not the match: an account the platform created stays in the ledger, and is removed when its current participant is deleted, even if a participant was later matched to it;
  - an account a living participant is bound to, or whose address is held by exactly one living account, as that account's verified primary address with the same first and last names. It is handed over to that participant instead, before any sign that the tenant has taken it into use is weighed (operator, 21 Oct 2026): a hand-over removes nothing, and that participant's own deletion asks every question again. A superadmin's Remove anyway still ends in this hand-over when such a participant has appeared since the hold, and both of its confirms say so;
  - the held cases, listed for a superadmin under Settings → Checkmarx One account removals: the tenant has taken the account into use (linked it to its sign-in provider; given it a group the platform could not have granted in that tenant; given it a role directly, beyond the one every new account gets and any it carried when the platform created it, or taken that default role away; set a detail on it that only the tenant's administrator can set, or one the tenant will not say whether only its administrator can set; added a password or sign-in method to it after the deletion was scheduled, or in the 15 minutes before, because the tenant's clock and the platform's are compared; or — where the platform recorded the address's fingerprint — changed its email), while a password, sign-in factor or pending action the account already had, a disabled or locked account and a verified address are the participant's own use and never hold it (operator rulings, 19 Oct 2026); the platform's key cannot prove it sees every role an account can carry, because it cannot view the tenant's clients (overridable, operator ruling 19 Oct 2026; asked only on the way to a removal, never before a hand-over); any other living account holds its address (re-checked weekly); the realm's record does not match what the platform created (this hold can never be overridden); or the creating installation cannot be confirmed (the row was recorded under a different `BASE_URL` origin — a copied database, or this installation after a `BASE_URL` change — or was recovered from history rather than recorded when the account was made); or a record of a living participant that names the account cannot be read (overridable, operator ruling 24 Nov 2026: the override waives only the unreadable records). A row whose participant vanished with no recorded deletion is listed as Not scheduled and is not acted on unless a superadmin schedules it.
  Failed removals are retried; a row gives up after 30 days and five attempts, and the account is then removed in the tenant by hand. A removal is never dropped for its age (operator ruling, 19 Oct 2026: the record is the only way left to finish the erasure in the tenant); one whose deletion is older than `EVENT_RETENTION_DAYS` is kept and flagged as kept past the retention period, on the list, on /metrics and in the app log. Apart from the by-design cases above, the residuals CLAUDE.md records under "F2 — a deleted participant's Checkmarx One account is removed from the tenant" (v8.12.7) and "P2 — the provisioning job's withdrawal re-asks whose account it is" (v8.13.1) are still open and NOT accepted. Among them:
  - an account the ledger never recorded cannot be reached: one created before v8.8.15, one created by a job that failed or stopped part-way before v8.12.7, one whose participant was deleted before a healthy boot could recover it from history, and one whose create got no answer or no usable id and was never recovered;
  - a restart forgets which removals were in flight, so a participant matched afterwards to an account whose removal may already have gone through is handed that account without the realm being asked first (one matched while a removal is known to be in flight waits for its answer instead, and a link made to an account the realm then says is gone is cleared and set up again);
  - the "taken into use" check does not read Checkmarx One's own Access Management assignments (whether they show among the account's role mappings has not been measured; the operator ruled on 19 Oct 2026 to ship with this recorded as an open residual), cannot see a detail the realm's user profile hides from the key, cannot see a second installation sharing the tenant when it grants a group with the same name as one of this platform's or binds the account through the email match, and skips the email check for rows with no recorded fingerprint, which includes every row recovered from history. Whether typical tenant keys may view the tenant's clients has not been measured either: a key that may not holds every removal as unprovable until a superadmin overrides it;
  - a revoked key gives no warning until a removal attempt fails;
  - ledger rows (user id, event, username, an unsalted hash of the address, the ids of the roles and names of the details the account carried when it was created) are kept after the participant is erased, until the account is withdrawn, passes to a living participant or the row is dismissed, however long that takes;
  - group memberships the platform granted to an account it did not create are not revoked when the participant is deleted;
  - projects and scans in the tenant are never touched.
- The public certificate page being crawlable and naming its holder, and registration surfaces carrying no consent copy, is acceptable by design. A page is published only when the holder presses Share, or when someone holding the certificate email presses the button on its LinkedIn share link (operator ruling, 17 Nov 2026: whoever holds the mail may press it, and the page says it publishes); pages from before Share was required stay published. Indexability is the feature rather than a missing robots meta.
- A Program having no default attempt cap is acceptable by design. Note the wrong-answer penalty IS shown to a Program participant — the pre-submit warning, the "−5 pts penalty" result and their running score are not gated by the kind of event — so guessing is priced, merely not bounded. (An Any-answer challenge and a quick question accept every answer, so they show no penalty, in every kind of event.)
- The all-solved auto-end counting a participant whose incomplete profile prevents them submitting is acceptable by design; the safe side was chosen deliberately, since the alternative would end an event out from under somebody about to complete their profile and play.
- `braces` (GHSA-vfj7-8cjw-p6xm) is no longer in the dependency tree: `package.json` overrides nodemon's `chokidar` to version 4, which does not use it (since v9.1.1). Report it if `braces` reappears in `package-lock.json`.
- A stale cached base IMAGE is not a production issue. The README's typical redeploy is `git pull`, `docker compose build --pull --no-cache`, `docker compose up -d --no-build`, then `docker image prune -f -a` (never `docker compose down` first, so a build that fails leaves the old version serving; since v9.2.9). `--pull` resolves the current base digest and `--no-cache` re-runs every build step, the runtime stage's `RUN apk upgrade --no-cache` included, so the image carries the Alpine fixes published since the last build; `docker-compose.yml` also sets `build.pull: true` (since v8.13.2). Do not report that a build through `docker-compose.yml` can start from an outdated cached base image, or ship an old `apk upgrade` layer, when the documented redeploy is followed. (A rebuild outside that recipe that keeps the build cache can still reuse an earlier `apk upgrade` layer; the README says so where it describes such a rebuild. The perf compose file, a throw-away measurement build, and a plain `docker build` do not pull; neither is a deployment path.)
- Three sign-in answers that differ by one database write are acceptable by design (operator ruling, 24 Nov 2026): an untie of an emailed code's event that clears a binding writes an audit row and one that finds nothing does not; a code request for an address nobody holds writes an address-proof row and one for an existing account does not; and once one IP address's budget for recording refusals is spent, a refusal is counted but writes nothing, so a caller who fills that budget learns one bit per IP address per window. The bodies and cookies are identical, and the timing gap sits behind the per-(IP, email address) and per-IP limits.

Audit posture:

- Re-audit from the current codebase each time.
- Recheck previously reported areas instead of assuming they stayed fixed.
- Exclude the accepted items above from findings unless the operator explicitly asks for a no-exceptions review.
